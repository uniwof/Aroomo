## 1. 核心思路：模型只做"读懂"和"说人话"，其他环节都交给脚本

资源管家是 AI成员，但它的大部分工作并不需要模型。省钱主要靠一条**漏斗**：

```
抓取(脚本) → 关键词初筛(脚本) → 去重(脚本) → 抓官方页(脚本)
   → [模型] 批量分类 + 从官方页抽取额度/到期日（JSON）
   → 校验写入(脚本) → 到期巡检(脚本) → 汇报(模板) / 私聊([模型])
```

每 100 条原始帖子，预计只有 5–10 条会交给模型处理。

## 2. 各环节由谁来做

| 环节 | 需要模型吗 | 由谁做（免费） | 说明 |
|---|---|---|---|
| ① 抓取 | 否 | Cloudflare Worker Cron（主账号已有 ai-groupchat Worker，**共用一个 Cron Trigger**，免费账号最多 5 个）；按分钟分配任务，每次只抓 1–2 个源 | 数据源：linux.do 分类/标签 RSS（实测公网可读）、V2EX RSS、Reddit `.rss`、HN Algolia API（关键词 free tier/credits）、GitHub Search API（新 awesome-free 仓库）、ygpy 等用户已有的源。**X/推特**见 §6 |
| ①b 用户丢链接 | 否（入口部分） | 置顶私聊 → Worker 直接放入队列 | X 链接用 `api.fxtwitter.com/<user>/status/<id>` 取全文（已验证可用，absorbed-resources） |
| ② 初筛 | 否 | 脚本：白名单关键词（API/额度/credits/免费试用/公益站/token/GPU/沙盒/TTS/生图…）+ 黑名单（单车/麦当劳/话费/银行开户…） | 实测样本里 linux.do「羊毛」标签 10 条有 7 条与公司无关（单车、麦当劳、话费、音乐会员），这一步能拦掉大头 |
| ③ 去重 | 否 | URL 规范化（去追踪参数）+ 官方域名 + 标题 simhash，与装备库和"已看过"表比对 | 同一个羊毛常被转发多次 |
| ④ 抓官方页 | 否 | 脚本：从帖子里提取外链 → 判断是否厂商自己的域名 → 抓取页面正文（HTMLRewriter 流式剥离 HTML） | 需要 JS 渲染的页面先标"待浏览器核实"，每周统一交给 GitHub Actions + Playwright（公开仓库免费）处理，或在用户要求时交给 Hark/Muse |
| ⑤ 分类打标签 + 抽字段 | **是** | 批量调用：一次 8–10 条，严格 JSON（类型=工具/素材/参考/方法、能做什么标签、免费额度、到期日、官方证据原句） | 能用规则判断的先用规则（github.com→方法/工具，已知厂商域名→工具），只有剩下的才交给模型 |
| ⑥ 核实判定 | 部分 | 脚本硬规则：额度/到期日**必须能在官方页原文里找到**模型给出的"证据原句"（字符串比对），找不到就标"未核实"，不进入主视图 | 落实"只认官方页、不骗用户"，同时防止模型编造 |
| ⑦ 写入 | 否 | 脚本写入 DO SQLite（只有资源管家有写入权限，成员只读，按 MCP/API 读取） | 记录字段沿用资源库规格：类型、标签、怎么用、额度/到期、最后验证时间、状态、出处 |
| ⑧ 到期巡检 | 否 | Cron 每天 1 次：到期前 7 天和 1 天写入提醒；每周重新抓一次官方页，用哈希对比是否有变化，页面返回 404 或"活动已结束"类字样时标记失效 | 只有官方页发生变化时，才交回 ⑤ 让模型重新抽取字段 |
| ⑨ 汇报 | 默认否 | 模板生成每日/每周摘要（新入库 N 条、即将到期、已失效），推送 Telegram/Bark | 用户眼睛不便，消息要少：**有新内容才发**，每天最多 1 条 |
| ⑩ 私聊对话 | **是** | 先用 SQL/关键词检索装备库，再把检索结果交给对话模型组织成中文回答 | 模型只负责"说人话"，不负责查找 |

## 4. 每月消耗估算（估算，标明假设）

假设：各源合计每天约 300 条新帖 → 初筛和去重后剩约 30 条 → 规则直接处理约 1/3 → 约 20 条交给模型（每批 10 条，约 2 次调用）；新候选的官方页抽取约 5 次；页面变化后的重新抽取约 1 次；私聊约 10 轮；摘要用模板，不调模型。

| 项目 | 次/天 | token/次（输入+输出） | token/天 |
|---|---|---|---|
| 批量分类 | 2 | ~4k+1k | ~10k |
| 官方页抽取 | 5 | ~3k+0.3k | ~17k |
| 页面变化后重新抽取 | 1 | ~3.3k | ~3k |
| 私聊 | 10 | ~2k+0.5k | ~25k |
| **合计** | **~18 次** | | **~55k** |

折算每月：约 **540 次调用、约 1.7M token**。只占 Groq 一个模型免费额度的很小一部分（单个模型每天 1K 次、200K token，即每天用量约为上限的 2% 次数 / 28% token）。
非模型部分：Worker 请求量每天几百次（免费上限每天 10 万次）；Cron 只占 1 个触发器；GitHub Actions 每周跑 1 次 Playwright，每次约 5 分钟（公开仓库免费）。
**结论：按这个规模，整套方案 0 元可以跑下来。**

风险点：Workers 免费档的 Cron **每次 CPU 时间上限 10ms**（等待网络的时间不计入）。解析大的 RSS 可能会超时。应对方法：每次 Cron 只处理 1 个源，用 HTMLRewriter 流式解析；如果还不够，把抓取和解析挪到 GitHub Actions 的 cron 里执行，Worker 只负责接收结果（同样免费）。

## 6. X/推特 和需要登录的源

- 免费、稳定的做法：**用户或 Poke 转发 X 链接 → 用 fxtwitter 取全文**（已验证可用）。另外抓官方博客、changelog、各平台自己的 RSS，这些往往比 X 来得更早，也更可靠。
- 自动抓 X 的时间线：需要用小号 cookie 配合 RSSHub 或 Agent Reach。按约定，用小号之前要先问用户，所以这项暂不开启。
- linux.do：公开分类和标签的 RSS 不需要登录。需要登录才能看的帖子仍由 Muse 或用户手动转发。
- 付费备选（默认**不推荐**）：X 官方 API 的付费档。为什么免费不够：它只在需要**全自动、实时**覆盖 X 时才有意义。价格开工前要在官方页核实，我这次没有核实。能换来什么：省掉转发这一步。对公司来说，转发加其他源已经够用。
