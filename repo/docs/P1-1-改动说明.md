# P1-1 改动说明：模型能力分类与负责人资格

日期：2026-10-24　基线：7aac775　范围：只做 P1-1。没有部署到任何 Cloudflare 账号，没有动线上资源，没用任何 Cloudflare 令牌或线上令牌；全部测试在本机 `wrangler dev --local` 上跑。交回后由 Hark 审核、复测并负责部署。

## 1. 改了什么

1. **结构化能力（caps）**：members.json 里每个成员都加了 `caps`：
   - `tags`：从 chat/vision/reason/code/write/image/video/audio 里取。
   - `context_window`：数字或 null。
   - `tool_call`：true / false / "unknown"。
   - `capability_status`：verified / pending。
   - `source`：数据来源说明。
   - 另外 `kind` 标出 agent / builtin。顶层 `_caps说明` 写明规则。
2. **负责人资格规则**（caps.js 里的 `leadEligibility`，前后端共用同一份结果）：
   - 能当负责人的模型必须**同时**满足：有 `chat`、`context_window ≥ 32000`、`tool_call === true`、`capability_status === "verified"`。
   - unknown 或 null 一律按不合格处理。
   - 生图、视频、音频、只会写作的成员和网页成员（web:true）只能当执行者。
   - 已退役的成员按 pending 处理。hark 和资源管家（builtin）不进下拉。
   - 能力数据来源：members.json 里 verified 实际是 7 个：4 个文字模型（models.dev 和 Workers AI 文档能对上）gpt-oss-120b、gpt-oss-20b、mistral-small-3.1-24b、qwen3-30b-a3b，加 3 个生图成员 agnes-image-2.5、agnes-image-2.1-flash、gpt-image-2.5（生图本身不能当负责人）。hark / 资源管家是 builtin，capability_status = n/a，不参与能力判定。其余都是 pending，要用户核实。（fix1 更正：原文写的「只有 4 个」不对。）
3. **后端强制**：`POST /api/lead` 在写入前先校验所有槽位，有不合格的就返回 400 `{code:"lead_ineligible", reasons, kind}`，lead_cfg 保持不变。
   - 副负责人接任（promoteSecondary）不会把不合格的副负责人升上去。
4. **前端下拉由服务端提供**：设置页里的负责人下拉只用 `GET /api/lead/candidates` 的 `candidates` 生成，不再在前端自己筛选。
5. **现任负责人不合格（例如能力被改回 pending）时**：
   - 不静默替换，lead_cfg 原样保留。
   - `GET /api/lead` 返回 `eligibility` 和 `notices`。设置页顶部出现 `#lsNotice`（role=alert），下拉里显示一个禁用的「当前：X（不合格：原因）」选项。
   - 派工时 leadPlan 会跳过这位负责人，按副负责人接任规则临时由副负责人派工；副负责人也不合格就回退到 Hark 内置规则。
   - 同时在资源管家私聊发一条通知（同一原因只发一次），说明「请你决定换人还是补核实」。
   - 用 'keep' 保存会被拦下。
6. **/v1/models 同步**（`syncRelayModels`，probeAll 时运行；也可以 `POST /api/models/sync` 手动触发）：
   - **不建成员卡**。
   - 模型名先归一化（`normModel`）：转小写；去掉 @cf/、厂商路径和 `:tag`；空格和下划线换成 -；去掉 -instruct/-it/-fp8/-awq/-latest/-preview 等后缀。
   - 已有成员的同名模型只补来源（kv `model_extra`）。
   - 新模型进候选池（kv `model_pool`，最多 500 条，按归一化名去重）。
   - 用户在页面上（cookie），或资源管家/操作员通过 `POST /api/models/pool/confirm` 确认后，才会成为自定义成员，能力是 pending，不能当负责人。`/dismiss` 用来忽略候选。
7. **能力核实**：`POST /api/member/:id/caps` 只接受页面 cookie。标 verified 必须写 source；`{reset:true}` 恢复默认值。
8. **MCP / 操作员技能**：新增工具 lead_candidates、model_pool、confirm_pool_model。skills/ai-groupchat-operator.md 已同步更新。
9. **deploy.py 重写**：
   - 全部配置从环境变量读取，不打印令牌，删掉了 Hark 沙箱路径。
   - 默认拒绝 ai-groupchat 和 chat.pcmanai.com，需要显式设置 `AGC_ALLOW_PRODUCTION=1`。
   - 子命令：build / upload / cron / workers-dev / domain / delete。
10. **测试脚本**：
    - test_live.py / ui_test.py 的**默认值不变**（仍是 https://chat.pcmanai.com 和原令牌文件路径；ui_test 默认代理仍是 http://127.0.0.1:8899）。
    - 新增环境变量切换：`AGC_BASE`（目标地址）、`AGC_TOKEN`（直接给令牌；也可 `AGC_TOKEN_FILE`）。其他可配置项：`AGC_CHROMIUM`（浏览器路径）、`AGC_PROXY`（设为空=直连）、`AGC_MCP_PYTHON`（装了 mcp+httpx 的 Python）。
    - testmode 快照新增 model_pool / model_extra / model_pool_dismissed / lead_inelig_note:*，测试结束后会还原。
11. **本机开发配置**：新增 `wrangler.toml`（只给 `wrangler dev --local` 用：DO SQLite 绑定 DB/ChatStore + migration v1、page.html 作 Text 模块、build 命令 `python3 deploy.py build`；不含账号 ID、不含密钥）。访问令牌放 `.dev.vars`（本机随机生成，`.gitignore` 已排除 `.dev.vars` 和 `.wrangler/`，不进提交也不进 zip）。

## 3. 两种负责人怎么区分

| | 配对外部负责人 | 模型负责人 |
|---|---|---|
| 来源 | 网页生成配对码 → 外部智能体 `POST /api/pair` 兑换，生成成员 `x-agent-*` / `x-hark-*` | members.json 里的模型成员，或候选池确认后的自定义成员 |
| 判定 | `paired:true`，或来源 kind=`pair`，或 id 匹配 `^x-(hark\|agent)-`（`isPairedId`）→ `leadKind = "paired"` | 其余有模型来源的成员 → `leadKind = "model"` |
| 资格 | **豁免能力规则**，rule=`pairing`；合不合格由配对本身决定，能力字段怎么写都不影响 | 按 caps 四个条件判断，rule=`capability` |
| 其他 | 外部智能体连接器（poke/webhook/telegram 等，kind=agent）按接入取得资格（rule=`connector`）；自定义 OpenAI 兼容端点由用户自己声明（rule=`user-endpoint`）；hark / 资源管家 = builtin，不能当负责人 | |

测试覆盖：单元测试「配对外部负责人豁免」「caps 写 image/pending 也不受影响」；test_live 的「配对负责人：在候选里、kind=paired、rule=pairing」「GET /api/lead 资格合格」「重新保存不被拒绝、成员不被删除」。

## 6. 已知问题

1. 自定义 OpenAI 兼容端点当负责人时由用户声明，不做能力校验（rule=user-endpoint）。
2. 同一个模型在不同提供方的上下文窗口不一样（例如 llama-3.3-70b 在 Workers AI 上只有 24000），caps 按主来源填写。中转站补的来源不改变 caps。
3. verified 的成员目前 7 个（4 个文字模型 + 3 个生图），其余要用户在页面上逐个核实（需要写来源）。
4. 操作员令牌（配对的外部负责人）也能确认候选池模型。新成员的能力是 pending，不能当负责人，风险可控；如果要收紧，可以改成只允许 cookie。
5. 现任负责人不合格的通知，同一槽位同一原因只发一次；原因变化才会再发。
6. deploy.py 只读环境变量、不打印令牌，本次没有运行（不部署）。
