# P1-6 第 3 条 · 备用入口方案（只出方案，未实现，等审核）

日期：2026-10-24。状态：**方案待审核**；需要用户提供第二个 Cloudflare 账号的限权令牌后才能做。费用红线：不升级 Workers Paid、不付款。

## 1. 先说清楚一个硬限制
- Cloudflare 免费版的「每天 10 万次 Worker 请求」是**按账号**算的。主账号超限后（错误 1027），主账号上**所有** Worker 都不响应，包括任何想去读主账号 Durable Object 的代理。
- Durable Object 只能被**同一账号**的 Worker 访问。第二个账号的 Worker 无法直接读写主账号的数据库。
- 所以「主入口 1027 时，备用入口实时读写同一份数据」在免费版上做不到。能做到的是：**备用入口只当一个「暂存发件箱」**，不形成第二套数据。

## 2. 推荐方案：备用入口 = 只收不存的暂存队列（store-and-forward）
```
平时：浏览器 ──► 主入口 chat.pcmanai.com（主账号 Worker + DO，唯一数据源）
主入口 1027 / 5xx / 超时：
      浏览器 ──► 备用入口 aroomo-relay.<子域>.workers.dev（第二账号 Worker + 自己的小 DO：只存待转交的消息）
主入口恢复后：主入口 cron（每小时）或页面重新连上主入口时
      主入口 ──拉取──► 备用入口 /relay/drain（HMAC 签名）──► 按 cid 幂等写进主库 ──► 备用入口删除已转交的条目
```
- **数据一致**：备用入口不保存项目、成员、Key，不跑模型，只存「用户发的消息 + cid + 房间号 + 时间」。主库仍是唯一数据源；转交用已上线的 cid 幂等（同一条最多写一次），所以不会丢、不会重。
- **前端切换**：`api()` 遇到 1027 / 5xx / 网络超时，发件箱里「待发送」的消息改投备用入口；备用入口回 `{queued:true}` 后页面标「已暂存到备用入口，主入口恢复后自动转交」。读数据（项目、成员）在主入口不可用期间显示上次缓存（PWA）并写明「主入口暂时不可用」。
- **主入口恢复后能看到同一条消息**：主入口 cron `17 * * * *` 和页面「重新连上主入口」时都会调 drain；验收用例：主入口模拟 1027 → 发消息走备用入口 → 解除模拟 → 主入口 drain → 项目里恰好出现一次。
- **页面怎么在主入口挂掉时还能打开**：现有 PWA（pwa.js）缓存了页面外壳；主入口 1027 时从缓存打开，页面再连备用入口。第一次从没打开过的设备无法使用（这一点做不到，要写进说明）。

## 3. 鉴权（不把主令牌给第二账号）
- 浏览器 → 备用入口：用一个**只能投递消息**的「暂存令牌」（主入口生成，HMAC(ACCESS_TOKEN, 'relay:'+日期)，有效 7 天，存浏览器 localStorage）。备用入口只验签名，不能读任何数据。
- 主入口 → 备用入口 drain：共享密钥 `RELAY_SECRET`（Hark 生成，两边各放一份 Worker secret，不进仓库、不进交接包），请求带时间戳 + HMAC，5 分钟内有效，防重放。
- 备用入口 CORS 只放行 `https://chat.pcmanai.com`；每条消息 ≤4000 字；每个暂存令牌每天最多 200 条（防滥用把第二账号额度也刷完）。

## 4. 需要用户提供什么
1. **第二个免费 Cloudflare 账号**（新邮箱注册即可；不绑卡、不升级）。
2. 在这个账号里建一个 **API 令牌**（My Profile → API Tokens → Create Custom Token），只给：
   - Account → **Workers Scripts: Edit**
   - Account → **Account Settings: Read**（读 account id / workers.dev 子域）
   - 账号范围：只选这个第二账号；**不要**给任何 Zone 权限、不要 Billing 权限。
   - 建议设 IP 不限、有效期 90 天。
3. 把令牌用「Hark 安全登录 / 保险箱」交给 Hark（不要发在聊天里）；告诉 Hark 账号 ID（可选，Hark 也能用令牌读出）。
4. 确认用 workers.dev 地址做备用入口（主域名 pcmanai.com 在主账号，第二账号不能挂它的子域；要自定义域名就得另买域名，违反费用红线，不建议）。

## 5. 实现与验收计划（审核通过后）
- 新文件 `relay.js`（备用入口，独立 Worker，约 150 行）+ worker.js 加 `/api/relay/token`、cron drain；page.html 发件箱加「改投备用入口」。
- 测试：test_live 加「备用入口拒绝无签名/过期签名」「drain 按 cid 幂等（同一条转交两次只出现一次）」；ui_test 模拟主入口 1027 → 消息经备用入口 → 解除后主入口能看到同一条。
- 部署顺序：先部署备用入口（第二账号）→ 主入口加 drain（读不到备用入口时静默跳过）→ 前端切换最后上线；任一步不全绿回滚。

## 6. 不推荐的做法（及原因）
- 备用入口做一套完整的 Aroomo（自己的 DO 存全部数据）：两套数据互不相通，违背「不得形成两套数据」。
- 备用入口反向代理到主入口：主账号 1027 时代理也打不通，没有意义。
- 把数据迁到外部数据库（两边都连）：要改全部存储层、引入新依赖和新密钥，风险和工作量都远超收益。
